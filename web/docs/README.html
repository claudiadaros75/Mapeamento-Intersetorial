1. Sobre o projeto

Este projeto é uma oportunidade de ação social, um exercício cívico alinhado com os objetivos da política de dados abertos, que preconizam utilização e o reuso dos dados públicos e abertos disponibilizados por fontes oficiais, como o IBGE e o Censo Escolar do INEP.

Inicialmente, o projeto estudou o georreferenciamento e a análise geoespacial, tendo como material de partida as Malhas Municipais Digitais (MMD) do IBGE, na edição de 2024. O objetivo foi aprender na prática conceitos fundamentais de cartografia, sistemas de coordenadas, projeções e manipulação de dados geoespaciais, documentando todo o aprendizado em arquivos Org (formato org-mode do Emacs).

Neste link: Entender os dados do IBGE expõe o que é a Malha Municipal Digital, onde baixar, formato e características técnicas.

Esta etapa cumpre um importante objetivo que é apresentação dos dados em mapas cujos polígonos são oficiais, provenientes dos conjuntos de dados oficiais do IBGE.

Existem muitos dados abertos disponíveis no Brasil, publicados por órgãos federais, estaduais, municipais e por organizações da sociedade civil, inclusive por meio de iniciativas que agregam vários painéis num só lugar. Alguns dos mais importantes:

5. Registro e divulgação do processo colaborativo (Contexto de Ciência Aberta)

Este projeto segue os princípios da ciência aberta: cada etapa do que é feito precisa ser auditável, ou seja, qualquer pessoa deve conseguir ver o que foi feito, por que foi feito, com quais dados e como reproduzir o resultado. Para isso usamos o Git e o GitHub, com o repositório público e todo o registro das etapas exposto nele.

O commit sozinho registra tudo, mas é granular demais para contar a história do projeto. Por isso combinamos várias camadas do Git/GitHub, cada uma com uma granularidade diferente: o commit é o rastro de auditoria, o Pull Request é a unidade de etapa e a Release é a unidade de divulgação.

5.1. Camadas de registro

Camada O que registra Papel na ciência aberta
Commit Cada alteração (o "como") Auditoria completa, linha a linha
Issue Uma pergunta, tarefa ou problema (o "porquê") Registra a intenção antes do trabalho e a discussão
Pull Request Uma etapa concluída (conjunto de commits) Resumo legível da etapa: o que, por quê, dados, reprodução
Milestone Uma fase que agrupa issues e PRs Mostra o andamento de cada fase do projeto
Tag + Release Um marco público, com notas de versão Divulgação: o que cada versão entrega
Zenodo (DOI) Arquivamento permanente de cada Release Torna cada versão citável e preservada fora do GitHub
GitHub Pages O site público (pasta web/) Divulgação dos mapas, da documentação e do diário do projeto

5.2. Fases (Milestones)

As fases seguem a delimitação do projeto:

  1. Fase 1 — Malhas territoriais do IBGE
  2. Fase 2 — Censo Escolar do INEP
  3. Fase 3 — Organizações da Sociedade Civil (IPEA)

5.3. Fluxo de cada etapa

  1. Issue: toda etapa começa com uma issue que descreve o objetivo e as fontes de dados, ligada à milestone da fase.
  2. Branch: o trabalho é feito num branch próprio, com nome descritivo (ex.: inep-censo-matriculas), em commits pequenos.

  3. Pull Request: a etapa termina com um PR para o main, seguindo o modelo do repositório:

    • objetivo da etapa;
    • dados usados (URL da fonte e data do download);
    • como reproduzir (comandos e scripts);
    • resultados obtidos;
    • decisões tomadas.

    O PR fecha a issue correspondente (Closes #N na descrição).

  4. Release: ao fim de cada fase, publica-se uma release (ex.: v0.1.0 — Malhas do IBGE). As notas da release são o texto de divulgação da fase, e o Zenodo gera um DOI para ela.

5.4. Convenção das mensagens de commit

As mensagens começam com um prefixo que indica o tipo da mudança, seguido de uma descrição curta em português:

  • feat: nova funcionalidade (script, mapa, painel)
  • data: inclusão ou atualização de dados
  • docs: documentação
  • fix: correção
  • chore: manutenção (configuração, organização)
  • ci: automação (GitHub Actions, Pages)

5.5. Peças que completam a auditabilidade

  • Licença: todo o repositório (código, textos e dados derivados) está sob a GNU GPL v3 (ver Licença).
  • Citação: um arquivo CITATION.cff na raiz, para o GitHub exibir "Cite this repository". Os metadados usados no Zenodo ficam em .zenodo.json.
  • Proveniência dos dados: os scripts de scripts/commands/ baixam os dados brutos das fontes oficiais; para cada arquivo, registrar a URL, a data do download e um hash (SHA-256).
  • Registro de decisões: escolhas importantes ganham um arquivo em docs/decisoes/ (ex.: 001-usar-cnefe-para-georreferenciar.org), explicando por que se escolheu uma alternativa e não outra.
  • Modelos no repositório: .github/pull_request_template.md e modelos de issue, para que todos registrem as etapas do mesmo jeito.

5.6. Automação: release → Zenodo (DOI) com trilha de auditoria

O workflow .github/workflows/zenodo-release.yml operacionaliza este fluxo. Sempre que uma release é publicada no GitHub, ele:

  1. exporta toda a trilha de auditoria do repositório para Markdown (script scripts/commands/github_auditoria__exportar_markdown.py):
    • cada issue e cada pull request, com descrição e linha do tempo completa (comentários, revisões, comentários em linhas de código, commits, rótulos, milestones, referências cruzadas, integração);
    • milestones, releases anteriores e o histórico de commits até a tag;
    • as respostas brutas da API do GitHub em JSON, sem perdas;
    • um arquivo SHA256SUMS para conferir a integridade de tudo;
  2. empacota o código da tag (...-codigo.zip) e a auditoria (...-auditoria.zip);
  3. deposita os dois no Zenodo pela API (script scripts/commands/zenodo__publicar_release.py), com os metadados de .zenodo.json, e obtém o DOI da versão;
  4. escreve o DOI nas notas da release e anexa o zip da auditoria a ela.

A primeira release cria o registro no Zenodo; as seguintes viram novas versões do mesmo registro. Cada versão tem seu DOI, e o "DOI conceito" aponta sempre para a mais recente.

5.6.1. Quando o pipeline roda

A publicação é automática, mas o gatilho é publicar uma release, não fazer commit ou push: no fluxo do projeto, cada release fecha uma fase.

Ação O pipeline roda?
Publicar uma release ou pré-release (botão Publish) Sim, automaticamente
Commit ou push em qualquer branch Não
Salvar uma release como rascunho (draft) Não; só ao publicá-la
Rodar à mão (Actions → "Release no Zenodo" → Run) Sim; serve para republicar uma release

O GitHub roda o workflow que existe no commit da tag da release. Enquanto o workflow estiver só no branch ibge_malhas, a release precisa ter Target = ibge_malhas; criada a partir do main, nada acontece. O botão "Run workflow" também só aparece para workflows que estão no main. Depois do merge de ibge_malhas no main, as duas restrições deixam de existir.

Configuração (uma vez só, por quem administra o repositório):

  1. Preencher os autores reais em .zenodo.json (campo creators, no formato "Sobrenome, Nome"); o workflow se recusa a publicar com o texto de exemplo.
  2. Criar tokens pessoais no sandbox do Zenodo e no Zenodo (escopos deposit:write e deposit:actions) e guardá-los como secrets do repositório: ZENODO_SANDBOX_TOKEN e ZENODO_TOKEN.
  3. Testar no sandbox: enquanto a variável ZENODO_SANDBOX não for false, as releases vão para o sandbox, com DOI fictício. Também é possível rodar o workflow à mão (aba Actions → "Run workflow"), informando a tag.
  4. Depois de validar, definir a variável ZENODO_SANDBOX = false.
  5. Após a primeira publicação, criar a variável ZENODO_CONCEPT_RECID (ou ZENODO_SANDBOX_CONCEPT_RECID) com o id indicado no resumo do job.
  6. Não ativar a integração GitHub do próprio Zenodo: ela criaria um segundo depósito, sem a trilha de auditoria.

5.6.2. Sandbox ou Zenodo real: como o destino é escolhido

Ao publicar uma release, quem decide é a variável ZENODO_SANDBOX (Settings → Secrets and variables → Actions → Variables). O padrão é sempre o sandbox, para que ninguém gere um DOI permanente por engano:

Variável ZENODO_SANDBOX Destino
não existe sandbox
qualquer valor diferente de false sandbox
exatamente false Zenodo real (zenodo.org)

Ao rodar o workflow à mão (aba Actions → "Run workflow"), a variável é ignorada e vale a caixa "Publicar no sandbox do Zenodo", que vem marcada.

Cada destino tem o seu par de configuração, sem mistura:

Destino Token (Secret) Registro conceito (Variable)
sandbox ZENODO_SANDBOX_TOKEN ZENODO_SANDBOX_CONCEPT_RECID
Zenodo real ZENODO_TOKEN ZENODO_CONCEPT_RECID

Como saber onde uma publicação foi parar:

  • nas notas da release, o sandbox aparece como "DOI (sandbox, teste)", com link para sandbox.zenodo.org; o Zenodo real, só como "DOI", com link para doi.org;
  • pelo prefixo do DOI: 10.5072/... é do sandbox (fictício, não resolve no doi.org); 10.5281/... é do Zenodo real (permanente);
  • no log do job, o passo "Escolher o destino" mostra Destino: sandbox.zenodo.org ou Destino: zenodo.org.

Na prática: para testar, apague ZENODO_SANDBOX (ou use true) e publique uma pré-release; para publicar uma fase, deixe ZENODO_SANDBOX = false. Uma publicação no Zenodo real não pode ser apagada: é possível criar uma nova versão, mas o DOI daquela versão é permanente.

7. Como rodar o pipeline das escolas (passo a passo manual)

Todos os comandos rodam a partir da raiz do projeto, com o ambiente Python do projeto (.venv/, ver 02-ambiente-python). Os dados baixados e os CSVs grandes ficam em data/ e não vão para o git.

7.1. 1. Baixar as bases oficiais

# Censo Escolar (INEP): 2025 para o pipeline novo; 2024 extraído para o ETL de 2024
.venv/bin/python scripts/commands/inep_censo_escolar__baixar_dados.py 2025
.venv/bin/python scripts/commands/inep_censo_escolar__baixar_dados.py 2024 --extrair

# CNEFE 2022 (IBGE), as 27 UFs (~3,9 GB). Não precisa extrair: o ETL lê
# o CSV direto do ZIP (extraído, o Brasil ocupa de 10 a 15 GB)
.venv/bin/python scripts/commands/ibge_cnefe__baixar_dados.py

7.2. 2. Exportar o Catálogo de Escolas do INEP Data (manual, no navegador)

O Catálogo de Escolas só exporta pelo painel do INEP Data (https://www.gov.br/inep/pt-br/acesso-a-informacao/dados-abertos/inep-data/catalogo-de-escolas), e corta cada exportação em 100.000 linhas. Por isso o Brasil é exportado por grande região (Norte e Nordeste, Centro-Oeste, Sudeste, Sul) e cada arquivo é salvo em data/cadastroescolar_inep/.

Atenção: a pasta deve ter só as exportações do painel. Qualquer outro CSV nela (por exemplo, uma cópia da base já juntada) faz o passo 3 parar, porque cada escola apareceria duas vezes.

7.3. 3. Juntar as exportações em uma base só

.venv/bin/python scripts/commands/inep_cadastro_escolar__juntar_exportacoes.py

Gera data/inep_catalogo_escolas.csv (210.320 escolas; endereço em um campo só e o ponto do INEP em Latitude=/=Longitude).

7.4. 4. Juntar o Censo Escolar 2025 ao Catálogo pelo código da escola

.venv/bin/python scripts/commands/inep_censo_escolar__juntar_cadastro_escolar.py

Liga CO_ENTIDADE (Censo) a Código INEP (Catálogo) e gera:

Arquivo Conteúdo
data/inep_censo_escolar_2025_+_cadastro_escolar_do_inep.csv todas as escolas, com JUNCAO_CENSO_CADASTRO dizendo em qual base estão
data/inep_censo_escolar_2025_+_cadastro_escolar_do_inep__nocadastro_forado_censo.csv só as escolas que estão no Catálogo e não no Censo
data/inep_censo_escolar_2025_+_cadastro_escolar_do_inep__nocenso_forado_cadastroescolar.csv só as escolas que estão no Censo e não no Catálogo

As escolas só do Censo são todas extintas: o Catálogo não lista escolas extintas.

7.5. 5. Casar as escolas com o CNEFE (coordenadas)

.venv/bin/python scripts/commands/escolas_dados__cruzar_censo_2025_cnefe.py          # UFs com CNEFE baixado (Brasil)
.venv/bin/python scripts/commands/escolas_dados__cruzar_censo_2025_cnefe.py am pa    # só algumas UFs

Separa o endereço do Catálogo (logradouro, número, CEP…), aplica o mesmo casamento em níveis do ETL de 2024 (1 e 2 por endereço, 3 e 4 por nome) e escolhe a coordenada final. Gera data/inep_+cnef.csv, com todas as colunas da entrada e mais:

Campo O que diz
JUNCAO_CENSO_CADASTRO censo_e_cadastro, so_censo ou so_cadastro
ENDERECO_SEPARACAO se o endereço tem CEP e número (cep_e_numero, sem_numero…)
NIVEL_CASAMENTO, STATUS_CNEFE, MOTIVO_GEOLOCALIZACAO como (ou por que não) a escola casou com o CNEFE
ALERTAS_GEOLOCALIZACAO o que merece conferência (CEP genérico, ponto compartilhado…)
LATITUDE, LONGITUDE, FONTE_COORDENADA, STATUS_GEOLOCALIZACAO a coordenada final e de onde veio (INEP ou CNEFE)
N_CANDIDATOS, SIMILARIDADE_NOME, nomes normalizados o "porquê" do casamento
CNEFE_JUNTADO e as colunas CNEFE_* a linha original do CNEFE inteira, quando a escola casou com ela
HISTORICO_PROCESSAMENTO as etapas que o registro percorreu, em ordem

7.6. 6. Gerar os dados do mapa de 2025 (Brasil)

.venv/bin/python scripts/commands/escolas_mapa__gerar_dados_web.py --ano 2025

Lê data/inep_+cnef.csv e as matrículas da Tabela_Matricula_2025 (no ZIP do Censo) e grava web/data/escolas_2025/ (um JSON por UF, ~34 MB no total), que a página web/escolas_mapa_2025.html carrega. Sem --ano, o script gera o mapa de 2024 (web/data/escolas/).

7.7. 7. Gerar os dados do mapa de auditoria de 2025 (Brasil)

.venv/bin/python scripts/commands/escolas_mapa__gerar_dados_auditoria.py --ano 2025

Lê de data/inep_+cnef.csv só as colunas da auditoria, confere cada ponto contra a malha municipal do IBGE (fora do município declarado?) e grava web/data/auditoria_2025/ (~51 MB), que a página web/escolas_auditoria_2025.html carrega. Sem --ano, gera a auditoria de 2024 (web/data/auditoria/).

Escolas extintas, paralisadas ou em atividade: coluna TP_SITUACAO_FUNCIONAMENTO do Censo (1 em atividade, 2 paralisada, 3 extinta).
